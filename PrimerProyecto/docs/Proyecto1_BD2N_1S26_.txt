2. Resumen Ejecutivo
Este proyecto está diseñado para que los estudiantes apliquen de manera integral sus
competencias en el diseño, implementación y consulta de bases de datos distribuidas
utilizando Apache Cassandra. El desafío central consiste en construir un sistema de gestión
de reservas de espacios compartidos que sea capaz de manejar grandes volúmenes de
datos con baja latencia y alta disponibilidad.

A partir del análisis de los requerimientos del negocio, los estudiantes deberán diseñar y
documentar un modelo de datos optimizado para Cassandra, aplicando estrategias de
denormalización controlada, particionamiento eficiente y claves primarias compuestas. Un
requisito fundamental de este proyecto es evitar el uso de JOINs y consultas con ALLOW
FILTERING, diseñando tablas especializadas según las consultas más frecuentes del
sistema.

Una vez definido el modelo, los estudiantes procederán a su implementación en un clúster
de al menos 3 nodos de Apache Cassandra. Esta fase no se limita a la creación de tablas;
se espera que los estudiantes configuren correctamente el Replication Factor, el
Consistency Level y las estrategias de compactación. Además, deberán insertar un volumen
significativo de datos y validar el comportamiento del sistema ante fallos de nodos, midiendo
el impacto en disponibilidad y rendimiento..

3. Enunciado del Proyecto
           3.1 Descripción del problema a resolver

Los estudiantes diseñarán e implementarán una base de datos distribuida en Apache
Cassandra, optimizada para la gestión de reservas de espacios compartidos en un sistema
de coworking o renta de salas de conferencia. El problema principal consiste en modelar los
datos de forma eficiente para un entorno distribuido, donde las consultas deben ejecutarse
con baja latencia sin depender de JOINs ni ALLOW FILTERING sobre grandes volúmenes de
datos.

El sistema deberá garantizar baja latencia en consultas mediante una correcta elección de
claves de partición, alta disponibilidad con configuración de clúster multi-nodo, eficiencia en
inserción y consulta para gestionar múltiples reservas simultáneas, y escalabilidad horizontal
asegurando rendimiento ante alta concurrencia.

Las entidades principales del sistema son:

Usuarios: personas que pueden realizar reservas. De cada usuario se debe guardar Nombre,
Email, DPI, Teléfono y NIT o CF.
Espacios: salas, escritorios o auditorios disponibles para reservar. De cada espacio se debe
guardar Nombre, Tipo, Capacidad Máxima y Ubicación.
Reservas: registros de ocupación de un espacio en un horario determinado. De cada reserva
se debe guardar el nombre, el usuario que reserva, el espacio reservado, Fecha, Hora Inicio,
Hora Fin y estado de la reserva.

Reglas de negocio del sistema:

Un usuario puede reservar varios espacios en diferentes fechas.
Un espacio solo puede estar reservado por un usuario a la vez en un mismo horario.
Las reservas pueden modificarse o cancelarse antes de la fecha de uso.
Se deben registrar horarios de uso, duración y estado de cada reserva.
Se deben permitir consultas de disponibilidad en base a espacio, fecha y usuario.

4.3 Requerimientos técnicos

Los estudiantes utilizarán Apache Cassandra como motor de base de datos distribuido para
el diseño, creación y manipulación de los datos. Se podrá utilizar Python para la generación
y carga masiva de datos mediante scripts automatizados.

El sistema estará basado en un entorno de coworking donde se gestionan reservas de
espacios compartidos. Los requerimientos técnicos específicos son:

Modelado de datos en Cassandra (Query-Driven Modeling):

El diseño del modelo lógico debe estar basado en queries: primero se identifican todas las
consultas que el sistema necesita responder y, a partir de ellas, se definen las tablas. Cada
tabla debe estar diseñada para responder una query específica de forma eficiente,
aplicando Primary Key compuesta con Partition Key bien definida. Los datos deben estar
denormalizados para optimizar consultas sin usar JOINs. Se deben crear múltiples tablas
especializadas, una por cada patrón de acceso identificado, para evitar ALLOW
FILTERING..

Configuración del clúster:

Implementar un clúster de 3 nodos en entorno local o mediante Docker. Configurar el
Replication Factor y el Consistency Level adecuados. Seleccionar y justificar la estrategia
de replicación entre SimpleStrategy o NetworkTopologyStrategy.

Inserción y consulta de datos:

Insertar al menos 100,000 reservas usando Batch Writes. Implementar las consultas CQL
requeridas por el negocio de forma eficiente. Documentar el diseño de cada tabla según la
consulta que soporta.

4. Metodología
Fase 1: Análisis de Requerimientos y Modelado Conceptual
Los estudiantes analizarán los requerimientos del sistema de reservas, identificando las
entidades principales, sus atributos y las relaciones entre ellas. Diseñarán el modelo
entidad-relación conceptual y definirán las consultas más frecuentes que el sistema debe
soportar, ya que en Cassandra el modelo se diseña en función de las queries.

Fase 2: Diseño del Modelo Lógico Basado en Queries para Cassandra
Transformarán el modelo conceptual en estructuras optimizadas para Apache Cassandra
siguiendo el principio de diseño basado en queries (Query-Driven Modeling): las tablas se
diseñan a partir de las consultas que el sistema debe responder, no de las entidades del
dominio. Identificarán y documentarán cada query requerida por el negocio antes de definir
cualquier tabla, y crearán tablas especializadas para soportar cada tipo de consulta de
forma eficiente. Aplicarán denormalización controlada, eliminarán relaciones tradicionales y
definirán las claves de partición y clustering de cada tabla justificando su elección en función
de la query que soporta.

Fase 3: Configuración del Clúster e Implementación Física
Desplegarán el clúster de 3 nodos de Apache Cassandra en entorno local o Docker.
Crearán el keyspace con la estrategia de replicación seleccionada y el Replication Factor
adecuado. Implementarán todas las tablas definidas en el modelo lógico mediante scripts
CQL.

Fase 4: Carga Masiva de Datos
Desarrollarán scripts en Python o CQL para insertar al menos 100,000 registros de reservas
en el sistema, utilizando Batch Writes para optimizar el proceso. Verificarán la distribución
de datos entre los nodos del clúster y validarán la integridad de la información cargada.

Fase 5: Implementación y Validación de Consultas
Implementarán todas las consultas CQL requeridas por el negocio, verificando que
funcionen de forma eficiente sin recurrir a ALLOW FILTERING. Documentarán el plan de
ejecución de cada consulta y medirán su latencia.


Fase 6: Pruebas de Escalabilidad, Tolerancia a Fallos y Documentación
Realizarán pruebas de tolerancia a fallos simulando la caída de nodos y midiendo el
impacto en disponibilidad y rendimiento según diferentes Consistency Levels.
Documentarán los resultados obtenidos, casos de prueba, métricas comparativas y
conclusiones del proyecto.
